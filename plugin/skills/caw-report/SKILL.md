# caw-report — 開発者向け動作レポート（匿名）

テストユーザーが caw を使う中で、**caw の機能が正しく働いているか・エラーが起きていないか・ディレクトリ構造が適切か**を、開発者がレビューできる形にまとめるスキル。出力は**完全に匿名**で、テストユーザーが安心して開発者に共有できる。caw-doctor が「ユーザー自身の構造を修復する」のに対し、caw-report は「開発者へ匿名のフィードバックを渡す」ためのもの。

## いつ使うか

- `/caw-report` を実行したとき
- 「開発者用レポートを作って」「動作レポートを生成して」「caw のレポートを出して」と言われたとき
- テストユーザーが一区切りついたとき、または進行役に状況を共有したいとき

`office/` が無ければ「まだ caw 環境がありません。`/caw` で作成してから実行してください」と促す。

## 絶対に含めないもの（最優先・PII 保護）

レポートには**次を一切含めない**。テストユーザーが外部に漏らしたくない情報を守るのが本スキルの最重要要件：

- **個人情報**：氏名・連絡先・学籍番号・所属・ORCID 等の ID
- **案件・プロジェクト内容**：企業名・業界名・研究テーマ・化合物名・論文タイトル・ES や志望動機の本文
- **ファイル名**：`companies/<企業>.md` や `papers/<著者-年>.md` のような**名前そのもの**（→ 件数だけを出す）
- **ファイルの中身**（一文字も引用しない）
- **絶対パス**：`/Users/<name>/…`・`/home/<name>/…`・`C:\Users\<name>\…`（→ 出さない。標準フォルダ名のみ）
- **研究分野・志望業界の具体名**（→ トラックは「研究 / 就活」までに留める）

出せるのは、**標準フォルダ名・件数・ファイルサイズ区分・放置日数・合否（OK/NG）・エラーの種別・バージョン・CLI・OS 種別・トラック・運用モード・日付（利用期間/最終活動）・ツールの有無**のみ。

## ワークフロー

### Step 1: 環境を匿名で把握する

- `office/`（Codex CLI は `office/AGENTS.md`、Claude Code は `office/CLAUDE.md`、Gemini CLI は `office/GEMINI.md`）の**冒頭メタのみ**を読み、トラック（`> トラック: 就活` の有無）と運用モード（`> 運用モード: はじめて` の有無）を判定する。**研究分野・志望業界などの本文は読み込まない／転記しない**。
- caw のバージョン（プラグイン/拡張の manifest があれば）・利用 **CLI とその version**・**OS 種別**（mac/Win/Linux）を把握する。
- **外部ツールの有無**を確認（`node -v`／`python --version`／`pdfinfo -v` 等の成否。バージョン文字列は控えて有/無で）。
- **MCP 連携**：`office/.mcp-setup.md` の有無と、設定済みサーバの**数**（API キー等は読まない・転記しない）。
- **日付系**：最古ファイルと最新更新ファイルの mtime から「利用期間（日数）」「最終アクティビティ日」を算出。`caw-report/` 内の既存レポート数で通番を出す。
- **ディレクトリは存在とファイル“数”だけ**を数える（`ls`／`stat` の件数・サイズ。名前は控える）。各ディレクトリで「空・極小ファイル数」「30 日以上未更新の放置数」も数える。

### Step 2: 点検（caw-doctor 相当・合否のみ）

次を OK / NG で判定する（パス・名前は出さず、合否と件数のみ）：

- ルート `office/` と設定ファイルが存在するか
- 秘書部 `office/secretary/{inbox,todos,notes}` が揃っているか
- 期待される部署が揃っているか（不足があれば**数**のみ）
- 統合 `inbox/` が存在するか
- START HERE 文書（`はじめにお読みください.md`）が存在するか
- **オンボーディング完遂度**：期待される部署・作業ディレクトリが揃って scaffold が完走したか（不足は**数**）、はじめてモードが維持/解除されているか
- **二層原則違反**（`office/<部署>/` 配下に成果物が書かれている）の**種別別件数**
- **規約外のトップレベルフォルダ数**（命名規約に無い独自フォルダの**数**。名前は出さない）
- **不可視（先頭ドット）フォルダの検知**（regression。`.` 始まりフォルダを caw が作っていないか）
- **設定ファイルの想定外肥大**（`CLAUDE/AGENTS/GEMINI.md` のサイズ異常の有無。**中身は読まずサイズのみ**で「不可侵ルール」逸脱の疑いを検出）

### Step 3: レポートを生成して保存する

`caw-report/` フォルダ（無ければ作成）に `caw-report/<YYYY-MM-DD>.md` を生成する。下のテンプレートに沿い、**件数・合否・種別のみ**で埋める：

```markdown
# caw 動作レポート（開発者用・匿名）

> 構造・件数・区分・合否・エラー種別・日付のみ。ファイル名・本文・氏名・企業名・研究テーマ・絶対パスは含みません。

## 1. 環境・互換性
- caw バージョン: <version / 不明>
- CLI: <Codex CLI / Claude Code / Gemini CLI / GitHub Copilot CLI> <version / 不明>
- OS: <macOS / Windows / Linux>
- トラック: <研究 / 就活> ／ 運用モード: <はじめて / 通常 / 詳しく / 不明>
- 外部ツール: Node.js <有/無> ／ Python <有/無> ／ poppler <有/無>
- MCP 連携: 設定ファイル <有/無>・接続サーバ数 <N>
- 利用期間: 約 <N> 日（最古ファイル〜本日）／ 最終アクティビティ: <YYYY-MM-DD>
- レポート生成: <YYYY-MM-DD>（このプロジェクトで <N> 回目）

## 2. オンボーディング完遂度
- [OK/NG] scaffold 完走（期待される部署・作業ディレクトリが揃っている）／不足フォルダ数: <N>
- はじめてモード: <維持 / 解除 / 不明> ／ START HERE 文書: <有/無>

## 3. 構造の健全性・逸脱（合否・件数）
- [OK/NG] office/ と設定ファイル ／ [OK/NG] 秘書部 secretary/{inbox,todos,notes} ／ [OK/NG] 統合 inbox/
- 二層原則違反（office/ 配下の成果物）種別別件数: <例: 旧パス: N>
- 規約外のトップレベルフォルダ数: <N>
- 不可視（先頭ドット）フォルダの検知: <無 / 有: N>（regression）
- 設定ファイルの想定外肥大（サイズ異常）の有無: <無 / 疑い>

## 4. 利用状況と完成度（件数・区分のみ・中身は非掲載）
| 標準ディレクトリ | 存在 | ファイル数 | 空・極小 | 放置(30日+) |
|---|---|---|---|---|
| companies/ | ○/× | N | N | N |
| documents/ | ○/× | N | N | N |
| self-analysis/ | ○/× | N | N | N |
| papers/ | ○/× | N | N | N |
| profile/ | ○/× | N | N | N |
| manuscripts/ | ○/× | N | N | N |
| presentations/slides/ | ○/× | N | N | N |
| inbox/（未処理） | ○/× | N | - | - |
- HTML 出力（caw-research/caw-events）: <有/無>
- voice-style/voice-self ・ profile/* ・ past-answers: <各 有/無>

## 5. スキル利用の痕跡（成果物の有無から推定・○/×）
- caw-research / caw-intake / caw-es / caw-interview / caw-events / caw-paper / caw-input / caw-slides / caw-playbook / caw-doctor

## 6. エラー・詰まり（種別のみ・メッセージ全文/パスは伏字）
- スキル別 × 種別の件数: <例: caw-es×外部API: N>（種別＝権限/not found/タイムアウト/外部API/構文/その他）
- caw-doctor 検出の構造問題（種別別件数）
- inbox 未処理: <N> ／ 空・極小の成果物: <N>
- hook 失敗回数（Claude Code 版のみ）: <N / 該当なし>

## 7. エンゲージメント・運用
- secretary: notes <N> ／ todos <N> ／ decisions（直近14日）<N>
- caw-doctor 実行痕跡: <有/無>

## 8. 間接検証シグナル（化学機能への含意）
- 踏まれたエンジンパス（成果物から推定・○/×）: オンボ＋scaffold / dispatch / 収集→構造化→可視化 / 生成→制約チェック / 反復→ログ / 統合 inbox 内容判定→振り分け / memory / doctor
- 就活トラックでこれらが機能していれば、対応する化学機能の同パスも健全（references/engine-validation-map.md 参照）

---
（caw-report が自動生成。個人情報・案件内容は含みません。テストユーザーはこのファイルをそのまま開発者へ共有できます。）
```

### Step 4: 自己点検（保存前に必ず）

生成したレポートを**自分で読み返し**、次が混入していないか確認する。あれば削除・伏字にしてから保存する：

- 絶対パス（`/Users/`・`/home/`・`C:\Users\` など）
- メールアドレス・`@` を含む文字列・氏名・企業名・研究テーマ・化合物名・論文タイトル
- ファイル名そのもの（件数に置き換える）
- ファイルの本文断片

### Step 5: 共有を案内する

- 保存先（`caw-report/<日付>.md`）を伝え、「**このファイルは匿名なので、そのまま開発者（進行役）に共有して構いません**」と案内する。
- caw が**自動で外部送信することはしない**（MCP 連携等で勝手に送らない）。共有はユーザーの手で行う。

## 重要な注意事項

- **匿名性が最優先**。少しでも個人情報・案件内容が漏れる懸念があれば、その項目は「件数」「○/×」に丸めるか省く。
- レポートは `caw-report/`（top-level・可視）に置く。`office/` 配下には書かない。
- 既存の同日レポートがあれば上書き確認、または `caw-report/<日付>-2.md` にする。
- 推測で埋めない。存在しない情報は「不明」と書く。
