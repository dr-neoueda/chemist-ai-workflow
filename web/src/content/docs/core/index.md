特定の AI CLI（Claude Code / Codex CLI / Gemini CLI / ChatGPT 等）に依存しない、**方法論のレイヤー**を扱います。実装 CLI が何であっても流用できる、部署設計・ファイル構造・運用ルール・品質ゲートの体系です。

## なぜ「部署化」なのか — チャット駆動の限界

AI チャットツール（ChatGPT / Claude.ai / Gemini Web 等）を単発で使う運用には、研究プロセスを支える基盤として明確な限界があります。

- **記憶の断絶**：セッションをまたいだ意思決定・学び・コンテキストが残らず、同じ説明を繰り返す
- **役割の混線**：一つのチャットで文献調査・計算・執筆・レビューを行うと、文脈が混ざり指示の精度が落ちる
- **品質保証の欠如**：生成物のレビュー責任が曖昧で、誤りが検出される機会が偶発的
- **再現性の不在**：誰かに引き継いだり半年後に再利用したりするときに、当時の判断根拠が失われている

**AI 部署化**は、これらの限界をファイルシステム上の構造で解決します。

- 部署 = 役割と責任が固定された AI エージェント単位（ファイルベース）
- 各部署は `CLAUDE.md` / `AGENTS.md` で自らのルールを宣言
- TODO・意思決定・学び・成果物は部署ごとのフォルダに蓄積される
- 過去の判断根拠は git 履歴 + decisions.md で検索可能

結果として、AI を **「研究プロセスの常駐スタッフ」** として扱えるようになります。

## AI 部署のテンプレート — 最小から最大まで

部署設計は固定スキーマではなく、研究テーマ・業務量に応じて段階的に拡張する設計です。

### 最小構成（1〜2 部署）

研究プロジェクトを始めた直後、または個人ブログ・ノート管理から AI 運用を始める場合：

| 部署 | 役割 |
|---|---|
| **秘書部** | 窓口・TODO・意思決定ログ・学びの蓄積 |
| **（任意）研究部** | 文献調査・要約・関心テーマの整理 |

### 中構成（3〜6 部署）

論文を読み始め、計算を回し始め、執筆も始まったタイミング：

| 部署 | 役割 |
|---|---|
| 秘書部 | 窓口・状態管理 |
| 文献部 | PDF → md → ナレッジベース自動登録 |
| 計算管理部 | 入力生成・ジョブ管理・log 解析・Playbook 蓄積 |
| データ解析部 | 解析スクリプト・可視化 |
| 論文執筆部 | LaTeX / Word での長文編集 |
| レビュー部 | コード品質・計算妥当性の二段レビュー |

### 最大構成（10 部署超）

著者が現在運用している構成。研究室として複数プロジェクトを並走する場合：

| 部署 | 役割 |
|---|---|
| 秘書部 | 窓口・TODO・意思決定ログ |
| 文献部 | 論文 DB・関心テーマトラッキング |
| 計算管理部 | 量子化学・古典 MD・周期系 DFT のジョブ管理 + Playbook |
| データ解析部 | 解析パイプライン・可視化 |
| 開発部 | Python ツール・CLI ユーティリティ・MLIP 訓練 |
| 論文執筆部 | LaTeX 原稿・図表・参考文献・査読対応 |
| 申請書執筆部 | 学振 / 科研費 / 学内グラント |
| プレゼン部 | スライド生成・図表・配色 |
| レビュー部 | コード・計算・原稿の品質ゲート |
| 実験記録部 | 装置 log・合成記録・測定データ管理 |
| ……（必要に応じて拡張） |

### 部署の追加・分割・統合の判断基準

新しい部署を作るタイミング：

- **頻度**：同じ種類のタスクが週 2 回以上発生し、毎回同じプロンプトを書いている
- **専門性**：他部署のルールと矛盾する固有の制約がある（例：申請書は字数固定、論文は字数自由）
- **責任分離**：生成と検証を別の AI に任せたい（レビュー部の独立）

部署を分割するタイミング：

- 一つの部署の `CLAUDE.md` / `AGENTS.md` が 200 行を超え、context window を圧迫
- 部署内の作業が明確に異なる責任を持ち始めた（例：論文部 → 論文部 + 申請書部）

部署を統合するタイミング：

- 二つの部署のルールがほぼ同一になった
- 部署間の連携コストが部署を分けるメリットを上回った

## ファイル命名と日次運用ルール

部署フォルダ内の標準構造：

```
.company/<dept>/
├── CLAUDE.md (or AGENTS.md)    # 部署のルール・責任・連携先
├── notes/                       # 日次の意思決定・学び
│   ├── YYYY-MM-DD-decisions.md
│   └── YYYY-MM-DD-learnings.md
├── todos/                       # 日次の TODO
│   └── YYYY-MM-DD.md
└── <成果物>/                    # 部署固有の出力
```

**1 日 1 ファイル + 追記運用**が基本ルール：

- 新規ファイルは日付で命名（`2026-05-15-decisions.md`）
- 同日内の追加はファイル**末尾に追記**（上書き禁止、過去の判断を残す）
- 翌日に持ち越す場合は新規ファイルを作り、前日からの引き継ぎを冒頭に明記

成果物（論文 md、スライド、解析結果）は **トップレベル**の作業ディレクトリに置きます（`papers/` `slides/` `analyses/` 等）。`.company/` 配下は運用情報・履歴のみで、Finder / Explorer から見えない場所に成果物を埋めない。これを **二層原則**と呼びます。

## 意思決定ログと学びの書式

### `decisions.md`（意思決定ログ）

過去の判断根拠を残し、半年後の自分・引き継ぎ先・指導教員レビューに耐えるフォーマット：

```markdown
---
date: "YYYY-MM-DD"
type: decisions
---

# YYYY-MM-DD 意思決定ログ

## <トピック>

### 状況
<何をやっていて、どこで判断が必要になったか>

### 判断
<採用した選択肢と、その理由>

### 代替案と却下理由
<検討した別案と、なぜ採用しなかったか>

### 残作業 / 次の判断点
<この判断から発生する次のアクションと、期日>
```

### `learnings.md`（学び）

セッション中に得たノウハウのうち、**未来のセッションに持ち越したいもの**だけを残します。

```markdown
---
date: "YYYY-MM-DD"
type: learnings
---

# Learnings YYYY-MM-DD

## <件名>

<状況・原因・教訓・参照先（jobs/, decisions.md, memory feedback）>

- **playbook 昇格**: 計算ノウハウなら該当 playbook の Lessons Learned に追記、不要なら「不要」
- **memory feedback 昇格**: 頻度の高いルールは AI のメモリに昇格、不要なら「不要」
```

両者は **書く側面が違うだけで、運用は対**：意思決定は「**判断**」、学びは「**経験**」を残します。

## 部署間連携 — 秘書を窓口にする理由

複数部署を持つと「どの部署に何を頼むか」が悩みになります。本メソッドでは **秘書部を全 AI 部署の窓口** に置き、ユーザーは秘書とだけ話す設計を推奨します。

- ユーザーが「計算をどう始めるか相談したい」と秘書に投げる
- 秘書が「これは計算管理部の領分です。引き継ぎます」と判断し、計算管理部の AGENTS.md / CLAUDE.md を参照しながら作業を進める
- 結果は秘書経由でユーザーに返り、意思決定が `secretary/notes/<today>-decisions.md` に記録される

この設計により：

- ユーザーは「どの部署に頼むか」を覚えなくてよい
- 各部署のルールは秘書が読み取って適切に適用する
- 全プロジェクトの意思決定が秘書部の `notes/` に集約され、横断的な振り返りが容易

部署間の直接連携（計算管理部 → レビュー部）も可能ですが、その場合も連携の意思決定は秘書部の `decisions.md` に記録するルールにしています。

## 品質ゲートの組み込み

生成された成果物は **必ず別の AI でレビュー** する習慣を組み込みます。

### 基本：単段レビュー

- コード：`code-reviewer` / `python-reviewer` / 言語別レビュー sub-agent
- 計算結果：物理量の妥当性、数値の単位、収束判定
- 文書：誤字・引用整合性・スタイル一致

### 応用：二段レビュー（Claude + Codex）

著者が常用しているパターン：

1. **Claude Code** が `python-reviewer` でコード品質（DRY / 構文 / 型）を見る
2. 直後に **Codex CLI** が同じファイルを物理意味論視点で見る（単位・物理的整合性・MD 自由エネルギー式の `-RT` 抜けなど）

両者が **異なる observation を出す** ことが期待値で、片方の AI で見落としていた誤りを他方が拾う実例が複数あります。詳細は応用編 [Claude + Codex 二段レビュー](/claude-code/two-stage-review/) を参照。

### ゲートのトリガー

品質ゲートは「いつ発火するか」をルール化する：

- `.py` を Write / Edit した直後 → コードレビュー必須
- 申請書ドラフト確定後 → 平易日本語チェック + 字数チェック
- 論文セクション編集後 → 文体プロファイル整合性チェック
- 計算 log 取得直後 → 収束判定 + Playbook の Lessons Learned 追記

## ベンダーロックインを避ける選択

本メソッドは **特定の AI CLI に依存しない設計** を保ちます。

- 部署フォルダのルールファイル名は `CLAUDE.md`（Claude Code）と `AGENTS.md`（Codex CLI / Gemini CLI）の **両方で読まれる** 形に保つ
- caw プラグインは Claude Code 版と Codex CLI 版で **同一の部署構成・Playbook 雛形** を配信
- ファイル構造・命名規則・運用ルールはすべて plain Markdown で、特定 AI の固有機能に依存しない
- Skills / Sub-agents / Hooks のような CLI 固有機能は **増分** として使い、メソッドの核ではない

ロックインを避ける設計の意義：

- 研究室のメンバーが **異なる CLI を使っていても** 同じ `.company/` で運用できる
- 数年単位の研究プロジェクトで **AI ベンダーが変わっても** 蓄積したノウハウが残る
- 個人アカウントでは Gemini CLI（OSS）、機関契約では Claude Code / Codex CLI、出先では Web 版、と **使い分けが自由**
